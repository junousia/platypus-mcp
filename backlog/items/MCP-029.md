# MCP-029 Define portable runtime storage traits

## Goal

Make SQLite an implementation detail instead of the architecture for runtime
state such as tasks, worker jobs, events, approvals, findings, and leases.

## Implementation Contract

Introduce explicit storage traits or equivalent typed boundaries for runtime
repositories. Keep the current SQLite backend as the only implementation, but
ensure feature modules depend on portable repository behavior rather than
SQLite-specific query details. Preserve the existing MCP tool schemas and local
file layout.

## Acceptance

- Runtime storage access is grouped behind typed traits or interfaces for
  tasks, events, approvals, findings, evidence, and future leases.
- The SQLite repository implements those boundaries without changing MCP tool
  behavior.
- Feature modules no longer need to know SQLite table or query details for
  migrated runtime operations.
- Documentation explains which state is repo-owned and which state belongs to
  the runtime storage boundary.
- Tests cover at least one migrated read path, one write path, and one error
  path through the portable boundary.

## Notes

Created after deciding that local-first must not become local-only. SQLite
should remain the default backend while the public architecture is expressed in
portable storage contracts.
