# MCP-125 Build reusable Pi workflow renderers

## Goal

Make Platypus output in Pi feel native, compact, and consistent instead of exposing raw JSON or generic tool text for common flows.

## Implementation Contract

Split the Pi extension UI into reusable renderers for project health, queue state, backlog creation, direct completion, work preparation, worker finish, findings, doctor output, and errors. Use Pi TUI primitives consistently and keep visual hierarchy compact enough for chat.

The renderers should summarize structured MCP results while preserving access to detailed data through the tool result details. Do not duplicate state transition logic in TypeScript; rendering must be derived from the MCP result envelope.

## Acceptance

- Common Platypus tool results render as purpose-built UI blocks rather than raw JSON.
- Queue and status widgets show project health, next ready item, active work, blocked count, and pending integration when available.
- Error rendering includes the failing action, the user-safe reason, and the next recovery action.
- Renderer functions are separated from tool registration enough to test in isolation.
- Snapshot or fixture tests cover representative completed, skipped, failed, and empty-state outputs.
